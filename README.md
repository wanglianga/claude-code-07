# 共享厨房长者配餐与志愿者送餐平台

面向社区长者的"中央厨房 + 志愿者送餐"一体化管理平台。覆盖 **长者用餐档案 → 营养师建议 → 厨房排餐 → 志愿者配送 → 异常闭环 → 住院停餐联动 → 补贴结算** 全业务链路。

## 原始需求

> 增加临时住院与停餐联动。家属或社区工作人员标记老人住院后，平台暂停后续配餐，并检查当天是否已经备餐、是否已经交给志愿者、是否还能转给备用名单。若餐盒已出库，志愿者需要选择退回厨房、转交同楼栋老人或报损；处理结果会影响补贴核销、厨房损耗和老人恢复送餐前的重新确认。老人出院后，社区工作人员需要重新确认饮食禁忌和送餐地址，再恢复排餐。

## 技术栈

| 层 | 技术 |
|---|---|
| 前端 | Vue 3 + Vite + Element Plus + Pinia + Vue Router |
| 后端 | NestJS 10 + TypeORM + JWT（RBAC 六角色） |
| 数据库 | PostgreSQL 16 |
| 部署 | Docker Compose（db / backend / frontend 三服务，仅前端发布宿主端口） |

## 一键启动

```bash
cp .env.example .env   # 可选，默认即可运行
docker compose up -d --build
```

启动后访问 `http://localhost:${CC_PUBLISH_PORT}`（默认 3000；本任务环境为 `http://host.docker.internal:3007`）。

- 首次启动自动建表并注入演示数据（10 位长者、8 个账号、昨日已完成配送、今日在途配送 + 草稿排餐、1 条住院中记录）。
- 验证方式 = 宿主 `docker compose up -d` 后浏览器/接口走通关键业务流；停止用 `docker compose down`（加 `-v` 清空数据重新演示）。

## 推荐演示路径（关键业务流）

### A. 临时住院与停餐联动（本需求核心）

1. **未备餐 → 直接取消**：`worker01` → 住院管理 → 住院登记 → 选「吴建国」（今日普通餐仍是草稿）。系统提示"今日餐尚未备餐，已直接取消"，排餐计划份数自动 -1，无损耗、不产生补贴。
2. **已备餐未出库 → 转备用名单**：`kitchen01` → 厨房排餐 → 确认今日「普通餐」排餐（不派单）；`worker01` → 住院登记 → 选「陈淑芬」。系统检查备用名单，自动把餐转给孙桂英（生成当日一次性用餐安排）。`kitchen01` 再"生成配送任务"，孙桂英的餐即补派成功。
3. **已出库 → 志愿者三选一处置**：
   - `family01` → 住院管理 → 为「张桂兰」标记住院（其餐盒 RL-001 已在志愿者手中）→ 生成待处置单；
   - `volunteer01` → 住院管理 → 处置 → 选「转交同楼栋老人」→ 选孙桂英（3 栋）→ 该餐计入孙桂英送达与补贴，不计损耗；
   - `family02` 为「李建国」标记住院 → `volunteer01` 处置选「退回厨房」→ 计入厨房损耗、不核销补贴；
   - `worker01` 为「王秀珍」标记住院 → `volunteer01` 处置选「报损」→ 计入厨房损耗。
   - 处置期间，志愿者在"路线详情"中会看到该任务被锁定（住院待处置），无法直接送达登记。
4. **联动结果核对**：`kitchen01`/`worker01` → 住院管理 → "厨房损耗"台账（退回 1 份 + 报损 1 份）；"餐盒处置"列表可见每单的补贴核销影响。`worker01` → 补贴结算 → 生成当月结算：孙桂英送达含转交餐，张桂兰/李建国/王秀珍当日不计送达。
5. **出院与恢复确认**：`worker01` → 住院管理 → 为「周福生」标记出院 → 状态变"出院待确认"（仍不排餐）→ 点"恢复确认"，重新核对饮食禁忌与送餐地址（可修改）→ 确认后恢复"正常"。`kitchen01` 生成次日排餐，周福生自动回到排餐名单。家属（`family01`）也可为自家老人标记住院/出院，但恢复确认只能社区办理。

### B. 既有主流程（排餐 → 配送 → 异常 → 结算）

1. **厨房** `kitchen01` → 厨房排餐：确认草稿 → 生成配送任务（连续未签收 ≥2 次 → 电话确认路线；观察/需探访 → 需熟悉情况志愿者路线；其余普通路线，每条 ≤5 户）。
2. **志愿者** `volunteer01` → 配送路线：接单 → 开始配送 → 送达登记（温度/签收人/老人状态/剩餐）或上报异常；老人状态选"较差"自动生成健康异常工单。
3. **社区** `worker01` → 异常工单：认领 → 办结（处理说明 + 餐食处理 + 可选长者状态调整）。住院相关状态已收归"住院管理"专门流程。
4. **社区/管理员** → 补贴结算：选月份生成结算单（实际送达 × 补贴单价，部分 6 元/餐、全额 12 元/餐；代收确认计入，异常退餐/住院退回/报损不计）→ 管理员确认结算。
5. **营养师** `nutrition01` → 营养建议：调整餐型（新建议生效，旧建议自动失效），次日排餐即按新餐型执行。

## 业务规则要点

- **排餐资格**：仅"正常/观察/需上门探访"状态长者参与；暂停、住院、出院待确认自动排除。
- **住院停餐联动**：家属或社区标记住院 → 老人状态变"住院"，自动取消未来待配送任务、退出后续排餐；当天餐按阶段自动处置：
  - 未备餐（排餐草稿）→ 直接取消，计划份数 -1，无损耗；
  - 已备餐未交志愿者（已确认排餐/已派单未接单）→ 优先转备用名单（同楼栋优先），无可用备用则计厨房损耗；
  - 已出库（志愿者已接单）→ 生成处置单锁定该任务，志愿者须选择：退回厨房（损耗）/ 转交同楼栋老人（计入接收人送达与补贴）/ 报损（损耗）。
- **补贴核销**：仅"已送达"计入（含代收确认、住院转交/转备用送达）；未备餐取消、退回厨房、报损均不计入。
- **恢复送餐**：出院后进入"出院待确认"（仍不排餐），社区工作人员重新确认饮食禁忌与送餐地址后才恢复"正常"，下一轮排餐自动纳入。
- **路线调整**：连续无人签收 ≥2 次 → 电话确认路线；观察/需探访/身体异常 → 安排熟悉情况的志愿者/助老员路线。
- **异常联动**：送达登记"老人状态较差"自动建健康异常工单；办结工单可调整长者档案状态并留痕（住院除外，须走住院管理）。

## 项目结构

```
├── docker-compose.yml      # db(内部) + backend(内部) + frontend(唯一发布端口)
├── .env.example
├── backend/                # NestJS：auth/users/elders/nutrition/dishes/kitchen/delivery/exceptions/hospital/settlements/stats + 种子数据
│   └── Dockerfile          # 多阶段构建，非 root 运行，HEALTHCHECK /api/health
└── frontend/               # Vue3 SPA，nginx 反代 /api → backend:3000
    └── Dockerfile          # 多阶段构建（vite build → nginx）
```
